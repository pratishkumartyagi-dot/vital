### rPPG signal quality: root cause + correction (2026-10-05)

**Symptom**: the front-camera rPPG "Signal: X%" readout reported 0-11% for signals whose heart rate was recovered essentially perfectly (e.g. POS pulse at 71.3 bpm against a true 72).

**Three independent defects in `computeSignalQuality` (`src/app/vital-monitoring/ppg-analysis.ts`)**, all now fixed:

1. **Bandwidth-biased "SNR"** (the dominant cause). It summed the 0.5-3.5 Hz cardiac band against the whole 3.5 Hz..`fs*0.4` range (~8.5 Hz wide at 30 fps, ~20 Hz at 60 fps) and then hard-clamped to 0 below SNR 1. The noise side is ~3x wider than the signal side, so ordinary sensor/codec noise drove the ratio under 1 and the clamp zeroed the whole score. Replaced by the exported `spectralSnr()`, which converts the reference band to its *equivalent in-band power* (mean bin density x cardiac-bin count), making the ratio a true matched-bandwidth SNR that is invariant to the reference-band width and frame rate. Scored on a log scale: SNR 0.5 -> 0, 2 -> 0.5, >=10 -> 1.
2. **Degenerate perfusion term.** `computePerfusionIndex(raw)` returns `AC/mean*100`, but the rPPG path analyses the POS pulse, which is per-window mean-normalized and therefore essentially zero-mean: the ratio was numerically unstable (measured anywhere from 0 to 15 000%) and, against a fixed threshold, pinned `piScore` at 1.0 for good signals *and* for pure noise — zero discriminative power. Two fixes: (a) AC is now the RMS of the already-bandpassed pulse and the DC comes from a new `dcRef` (the green skin-ROI mean) threaded through `analyzeHeartRate(ppg, fs, dcRef)` / `AnalyzeOptions.dcRef`, auto-derived from `greenSignal` in `analyzeVitals`; (b) `posPulse` now rescales its output by `sqrt(3) * mean(green)` so the pulse is in **camera-count units** instead of per-unit relative amplitude (two unit mismatches were at play: the projection's 1/sqrt(6) factor, and dividing a dimensionless signal by an absolute count level). POS AC/DC now reads 3.21% vs 4.89% for the same signal's raw green channel, instead of 0.03%.
3. **Inverted pulse gate.** The "filtered SNR" gate compared the cardiac band of an *already-bandpassed* signal against its own numerically empty 3.5-12 Hz tail, and its zero-floor fallback of `8` sat **below** the gate's own zero crossing of `10` — so a perfectly clean pulse scored `pulseGate = 0` and SQI 0. Replaced by `cardiacSpectralProminence()` (cardiac-band peak/median, which has no degenerate branch and cleanly separates real pulses from a Gaussian floor).
4. Minor: a single RR interval substituted `cv = 100`, scoring a two-peak signal as fully irregular; it now uses 0.

Also fixed: `extractCreatinineFeatures` fell back to `redPI` when `ppgPI` was 0 (always, for the zero-mean POS pulse), reading the front-mode perfusion descriptor off the *weakest* channel — order is now `ppgPI || greenPI || redPI`.

No SQI built on magnitude statistics can separate it; only a pulse-shape/plausibility model can.

**Second pass — SQI ceiling at 50–75% on real facial rPPG (2026-10-05 follow-up)**:
After fixing the bandwidth/ perfusion/ pulse-gate defects, realistic simulated signals still plateaued at 50–75. Root cause: `detectPeaks` + the fixed 300–2000 ms acceptance window let dicrotic-notch features through as peaks (333–550 ms gaps vs true ~833 ms RR). The resulting alternating long/short RR intervals inflated the raw CV from ~3% to 23%, so `regScore` collapsed to 0.41–0.55 and capped SQI at ~75 even though the pulse itself was strong. Two-part fix: (1) `analyzeHeartRate` now scales the acceptance window to a robust estimate of the beat period (`refractoryMs = max(300, 0.55 × periodEstimate)`), rejecting any candidate closer than 55% of a cycle — enough margin over the ~45% RR upper bound of the dicrotic notch while keeping real beats; (2) `computeSignalQuality`'s regularity term is now computed on the **ectopic-filtered RR series** (already available) using a robust MAD-based CV (`1.4826 × MAD / mean`) rather than the standard deviation, so a handful of residual mis-detections don't masquerade as an irregular rhythm. Amplitude-first peak selection was tried and rejected: it removes notches more aggressively but produced measurably worse HR under auto-white-balance drift (66.3 vs 69.7 bpm on the realistic path) because the drift changes which local maximum is tallest. Realistic-path SQI after both fixes: 85 → 99 (was 97 with only the first fix, but the MAD robustness brings regScore from 0.70 to 1.0 for the realistic path). `page.tsx` and `training/ppg_analysis.py` unchanged. `bun typecheck`/`bun lint`/`bun run build`/`bun run test:ppg` (45/45) all pass.

## Technical Specifications

- **Framework**: Next.js 16 + React 19 + TypeScript
- **Styling**: Tailwind CSS 4
- **Signal Processing**: FFT-based HR estimation (0.5-3.5 Hz bandpass)
- **Analysis Module**: `src/app/vital-monitoring/ppg-analysis.ts` — HeartPy-style peak detection + HRV (SDNN/RMSSD/pNN50) + RRest-style respiratory rate (autocorr/FFT/peak fusion) + POS chrominance pulse (`posPulse`, Wang et al. 2017) + Hann-windowed `powerSpectrum` + creatinine morphology features (`extractCreatinineFeatures`/`estimateCreatinine`, age-term-free with mode-specific bands and SQI ≥ 40 gate) with CKD-EPI 2021 eGFR (`estimateEgfr`) and KDIGO staging (`kdigoStage`); DC-seeded `butterworthBandpass` (no filtfilt edge transient). **BP Estimation**: Fast morphology-based surrogate (`estimateBloodPressure`) + optional CNN-BiLSTM-Attention deep learning (`analyzeVitalsWithDeepBP`, TF.js in browser, `bpDeep` field). **Respiratory Rate**: Camera-mode-specific — rear PPG uses RRest (BFi + ACF/PKS/ARP fusion, browser-native TS in `rrest-resp.ts`); front rPPG uses POS pulse + bandpass + autocorr/FFT/peak fusion (`extractRPPGRespiration`).
- **Python Reference**: `training/ppg_analysis.py` using `heartpy` + `RRest` for offline validation
- **Models**: SCNN_8rois (1D CNN with attention over 8 ROIs), **BPNet** (CNN-BiLSTM-Attention for cuff-less BP from PPG, Mohammadi et al. 2025)
  - **Training**: PyTorch with 5-fold cross-validation
  - **Dataset**: MCD-rPPG (600 subjects, multi-camera) + **BIDMC** (contact PPG for ROSE-Net cross-domain pre-training)
  - **Package Manager**: Bun

| 2026-10-06 | **Contact PPG SpO2 / RR / Hb accuracy fix — "grossly low" values**: User reported SpO2, respiratory rate and haemoglobin from contact fingertip PPG were grossly low compared with ideal. Root causes and fixes: (1) **RR ~0 for rear camera** — `page.tsx` passed `analysisSource` (the 0.5-3.5 Hz bandpassed cardiac pulse) as `respSource` to `analyzeVitals`. Respiration modulates the PPG at 0.05-0.5 Hz (baseline wander, amplitude modulation, frequency modulation), which is *below* the cardiac band, so the estimator received no respiratory signal. A smartphone camera has no IR channel, so the accepted proxy is red/green, where R is ~0.6-1.8 because green (550 nm) is absorbed far more strongly by haemoglobin than red (660 nm). Replaced with red/green calibration constants `SPO2_RED_GREEN_*` (intercept 106, slope 8, range 88-100) and a new `estimateSpo2RedGreen` helper that applies the ZLO correction.
